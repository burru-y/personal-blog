做登录的时候，JWT 看起来是最省事的选择：服务端签发，客户端保存，之后每次请求带上就行，不用查库。

直到我遇到一个问题：**用户改了密码，旧令牌还能继续用七天。**

## 无状态的代价

JWT 的验证只看两件事：签名对不对、有没有过期。它不关心这个令牌是不是「已经被作废」。

这就意味着：

- 改密码之后，别人手里那个旧令牌还有效
- 把某个账号踢下线，做不到
- 令牌泄露后，唯一的办法是等它过期

本质原因是**服务端不记录任何状态**。省下的那次数据库查询，代价全在这里。

## 常见的三种解法

### 方案一：黑名单

把要作废的令牌存进 Redis，每次验证查一次。

问题：**又查库了**，等于放弃了无状态的好处，还要多维护一个组件。

### 方案二：短过期 + 刷新令牌

访问令牌 15 分钟过期，刷新令牌存数据库。改密码时删掉所有刷新令牌，15 分钟后旧访问令牌自然失效。

问题：还是有 15 分钟的窗口。对大多数场景够用，但不是立刻生效。

### 方案三：版本号

在用户表加一个字段：

```sql
alter table users add column token_version int not null default 0;
```

签发令牌时把它写进 payload：

```json
{ "sub": "用户ID", "role": "MEMBER", "tv": 7, "exp": 1792945914 }
```

每次验证多查一次库，比对 `tv` 和数据库里的值。**改密码时把 `tv` 加一，所有旧令牌立刻失效。**

```java
if (principal.tokenVersion() != user.getTokenVersion()) {
    throw new BusinessException(ErrorCode.UNAUTHENTICATED, "登录已失效，请重新登录");
}
```

## 为什么我选了版本号

因为它是一个**明确的取舍**：

| 方案 | 立刻生效 | 需要额外组件 | 每请求查库 |
|---|---|---|---|
| 黑名单 | ✅ | Redis | ✅ |
| 短过期 + 刷新 | ❌ 有窗口 | 无 | ❌ |
| 版本号 | ✅ | 无 | ✅ |

版本号和黑名单都要查库，但版本号不需要 Redis，实现只有几行。

代价是每次请求多一次数据库查询。这个代价我认为可以接受——比起「密码泄露后七天内令牌都能用」，多一次索引查询太便宜了。

## 一个容易忽略的细节

`token_version` 必须在**所有**令牌验证路径上都检查：普通请求、刷新令牌、AI 服务的独立验签。

我一开始只在主流程里检查了，刷新令牌那条路径忘了，结果改密码后还能用刷新令牌换出新令牌——等于没作废。

教训是：**安全机制要把所有入口列出来，逐个确认，而不是改一处就以为好了。**

## 顺便说一下密码存储

用的是 BCrypt，cost 12。

不要用 MD5/SHA256 存密码，也不要用「加盐哈希」自己发明方案。BCrypt 的设计目标就是慢——单次验证约 100ms，正常登录感觉不到，但暴力破解的成本被放大几万倍。

## 小结

JWT 不是「更好的 Session」，它是**另一种取舍**：把状态从服务端移到客户端，换取水平扩展的便利。

如果你的场景需要「立刻踢人下线」，就必然要为这个能力付出一次查询。想清楚要什么，比选哪个技术更重要。
