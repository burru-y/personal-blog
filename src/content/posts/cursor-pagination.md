列表页要分页，最直觉的写法是 `?page=2&size=20`，对应 SQL：

```sql
select * from projects order by created_at desc limit 20 offset 20;
```

数据量小的时候没问题。但只要**有人在翻页过程中发布了新内容**，问题就来了。

## 页码分页的两个 bug

假设列表按时间倒序，第一页是最新 20 条。

**漏记录**：你正在看第 1 页，有人发了一条新内容。它排到最前面，原来的第 20 条被挤到第 21 位。你点第 2 页时 `offset 20` 跳过的是「新的前 20 条」，原来第 20 条你没看到，直接消失了。

**重复记录**：反过来，如果有人删了一条，第 1 页的最后一条会滑到第 2 页的第一条——你在两页里看到同一条。

这不是偶发情况。一个活跃站点上，翻页的几秒钟内数据几乎一定在变。

## 游标分页怎么做

不用「跳过多少条」，而是「从哪条之后继续」。

```sql
select * from projects
where (created_at, id) < ($1, $2)
order by created_at desc, id desc
limit 20;
```

`($1, $2)` 是上一页最后一条的时间戳和 ID。数据库里给 `(created_at, id)` 建索引，这个查询走索引扫描，翻到第 100 页和第 1 页一样快——而 `offset 10000` 需要先扫过前面一万行。

### 为什么游标里要带 ID

只用时间戳会有问题：同一毫秒创建的两条记录，没法确定先后。加上 ID 做兜底比较，顺序才是唯一的。

### 游标长什么样

给客户端的是 base64 编码的字符串：

```
MjAyNi0xMC0yNlQxMjozNDo1Nnw0ZjNh
```

解开是 `2026-10-26T12:34:56|4f3a...`。

用 base64 而不是明文 JSON，纯粹是为了**不让客户端依赖这个格式**——哪天内部结构改了，客户端无感。

## 接口返回的形状

```json
{
  "items": [ ... ],
  "nextCursor": "MjAyNi0xMC0yNlQxMjozNDo1Nnw0ZjNh"
}
```

没有 `total`、没有 `page`。想要「共多少条」得单独查一次 `count(*)`，这是游标分页的代价：**它不擅长回答「我在第几页」**。

如果确实需要页码（比如跳转到第 50 页），那就不是游标分页的适用场景，老实用 offset + 限制最大页数。

## 什么时候不该用游标

- 需要跳页（「跳到第 10 页」）
- 需要显示总数和页码
- 数据量小（几千条以内，offset 开销可以忽略）

## 实现细节

排序字段和游标字段必须**完全一致**，否则会跳过或重复：

```java
// 排序
order by created_at desc, id desc

// 游标条件（注意同方向）
where (created_at, id) < (:cursorTime, :cursorId)
```

还有一个坑：`limit` 要限制上限。用户传 `limit=100000` 会把内存打爆，我这边限制在 1–100，超出直接截断。

## 小结

游标分页解决的是**一致性**问题，不是性能问题（虽然性能也更好）。

如果业务上不需要跳页，它的复杂度也就多一个游标字段的编解码，换来的是「翻页时永远不漏不重」。这个交换是值的。
